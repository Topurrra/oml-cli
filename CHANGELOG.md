## 1.9.0

### Added
- A human terminal view for the commands developers type themselves (`--help`, `version`, `doctor`, `check`, `architecture`, `image`, `font`, `setup`, `log`, `library`, `skills`, `templates`, `meta`, `expr`, `api`, `widgets`), when stdout is a console and the command is not inside `oml run`. The agent-loop commands (`inspect`, `describe`, `apply`, `spec`, `run`, `validate`, `review`, `memory`, `doc`, ...) keep JSON in a console too, because some harnesses run agent commands in a real terminal; `OML_OUTPUT=human` gives them the human view. The view has: titled sections, aligned key/value lines, tables for arrays of objects, indented lists, and the `error`, `hint`, `warning` and `attention` fields first and highlighted. The JSON contract does not change: a pipe, a file, `--json`, `OML_OUTPUT=json` or `oml run` still get today's exact JSON, byte for byte. `--json` forces JSON; `OML_OUTPUT=json|human` overrides the default either way. Colors are ANSI virtual-terminal sequences, only on a console that supports them, and respect `NO_COLOR` and `TERM=dumb`; no meaning relies on color, and box and bar characters fall back to ASCII when the output encoding cannot show them. Long values wrap to the console width; paths are never cut, a table that would cut a cell or hide nested samples prints each row as its own block, and a cut list points to `--json`.
- Recipe gallery in the dashboard: the per-recipe "Copy prompt" button is gone; a "Prompts for agents" section at the top offers two ready templates — "Small task" and "Architect" — each with a when-to-use line and a Copy button.

### Changed
- oml memory: the store is in the project root folder (the current folder, or --dir). --module <file.oml>
gives only the module name; it no longer moves the store to the module's folder.
- The dashboard prompt builder is ordered as numbered steps (1 Modules, 2 Task, 3 Elements from other modules, 4 Limits) with a "Small task"/"Architect" choice at the top; the generated task starts with `[oml] Small task` or `[oml] Architect task`. The preview option now reads "Preview the UI at 1366 and 1920 px (add dark or 390 px only when needed)".
- The architecture page never zooms automatically: selecting a module, opening or closing an application, showing the Platform group, and clicking a finding keep the current zoom level (the selection highlight and side panel stay). Keyboard focus pans only when the focused card is outside the visible area, and never zooms. Manual zoom, wheel and keys, and the Fit button are unchanged.
- `oml memory init` keeps the wrong-folder check when `--module` is given: only a module file inside the folder tree (or `--force`) skips it. The cookbook and docs example for `init` now uses `--dir`.
- The architecture page pans to keep the newly selected modules in view (a clicked module, an opened or closed application, shown platform modules, finding modules) without ever changing the zoom level.

### Fixed
- `inspect` lists a screen's roles in a fixed order, and `census` orders equal counts by name: both changed from run to run before.
- `tests/terminal-check.ps1` compares golden outputs independent of line endings; `.gitattributes` keeps the golden files at LF.
- `oml --help` and `oml <command> --help` group commands by area (Read, Change, Preview, Service Studio, LifeTime, Knowledge, Assets, Maintenance) with the command names highlighted, when shown in a console.
- Progress on stderr for slow commands in a console only, like `oml library fetch`: `pull`, `publish`, `lt download`, `app extract`, `architecture --team` and `check --team`.
- `tests/terminal-check.ps1`: the renderer's unit-style self-tests (`oml terminal-test`), byte-identical JSON vs 1.8.0 goldens for 11 redirected commands, and the `--json` / `OML_OUTPUT` / `NO_COLOR` rules.

## 1.8.0

### Added
- `oml meta <file.oml>...` reads a module header without loading the model (name, version, upgrade level, key, hashes, signature, type). `oml meta --diff <a> <b>` lists the header fields that differ, for example after a pull or a save.
- `oml expr "<text>"` parses one OutSystems expression: `ok` and its canonical form, or the error with its position (exit 1). Checked on 2,077 real expressions from two modules with no failure.

- `oml app check <package> --producers <folder|package> [--deep]`: missing producers, changed module types and, with `--deep`, consumed elements the producer lacks (`--deep` is not yet verified on a real application with references).
- `oml app list` and `app extract` read the package manifest directly when there is one (faster; no model load). `extract` falls back to the model when a module of the manifest has no file in the package.
- `insertNodes` places one inserted node on its link and keeps the rest of the flow layout. Several inserted nodes still get a full lay-out.
- `oml review` ignores expression changes in spacing and keyword case only.
- `OML_EXPR_STRICT=1` makes `apply` refuse an expression that does not parse.

### Fixed

## 1.4.0

### Images: ICO, PNG to SVG, SVG optimization

- `oml image <input> --to ico [--sizes 16,32,48]` writes a real multi-size icon from any raster image or SVG (each size drawn from the vector). Frames up to 48 pixels are 32-bit BMP with a transparency mask, larger ones PNG. A non-square image is centred on a transparent square. Default sizes `16,32,48` (favicon); `--sizes 16,24,32,48,64,128,256` for an app icon. A size list with a word, an empty item, a repeat or a size outside 1-256 is refused, and so are `--sizes` without `--to ico` and `--max-width`/`--max-height` with it. Windows' own icon loader, `System.Drawing.Icon` and Chrome read the files.
- ICO input now always works (before: "this build may not support ICO"): oml reads the file itself and takes the largest frame, PNG or BMP (32-bit, 24-bit and palette frames with their transparency mask). A cut-off or foreign file gets a clear error, and so do a PNG frame over 100 million pixels (checked before decoding) and a palette larger than its colour depth. ICO input needs an explicit `--to`. A very wide image is scaled down before it is padded to a square, so a 20000 x 100 strip stays small in memory.
- `oml image <logo.png> --to svg` traces a raster image to vector paths (our own code, no Potrace or other GPL code): a palette from the flat colours (auto, at most 16; `--colors N`), one `<path>` per colour, layers that overlap so no background shows between colours, sub-pixel outlines from the anti-aliasing, sharp corners, cubic Béziers within `--tolerance` pixels (default 0.3), holes kept, speckles under `--min-area` removed, `--alpha-threshold`. For a photo or gradient the report adds a note that suggests `--mode embed`, which puts the PNG inside an SVG as it is; semi-transparent areas (shadows) also get a note. `--transparent-bg` leaves out a background colour that fills the border. Alpha at exactly `--alpha-threshold` counts as opaque. Lower layers reach only 2 pixels under higher ones, so thin letters next to bolder ones stay clean, and narrow line ends keep both corners. Tracing options on an SVG input are refused (noted in a batch). Before, raster to SVG was refused. On four test drawings (two-colour logo, flat icon, text, shapes with holes) at most 0.08% of the pixels differ from the source PNG; a 1024 x 1024 logo traces in under a second.
- SVG to SVG is now an SVGO-style optimizer (our own code): editor data, definitions without an id, empty groups, safe initial values and needless groups go; colours and path data take their shortest form; transforms are applied to paths and neighbouring paths merged when nothing can see the difference. The default is safe for `<img>`, inline SVG under page CSS and sprites: it keeps every id with its definitions, style attributes, explicit inherited values such as `fill="#000"` and element names, and leaves transforms with `transform-origin`/`transform-box` alone. `--remove-ids` drops ids and definitions nothing in the file uses; `--aggressive` (for `<img>` and CSS backgrounds only) adds that, style attributes to presentation attributes, inherited initial values and shapes to paths. Title, desc, text and the viewBox stay; a `<style>` element keeps the structure, scripts and animation keep every element. The default precision follows the viewBox size. Every result is drawn with Svg.Skia against the original: if the pixels change, a higher precision is tried, and otherwise the original bytes are written with `details.kept` and the reason. A plain DOCTYPE (old editors) is now accepted; one with its own declarations is still refused. `--strip-title` also removes `<desc>`. On 47 real SVGs: 36.5% smaller by default (36.7% with `--aggressive`), and Chrome draws every result like its original.
- `oml image batch <folder> --to ico` and `--to svg` (traces raster images, optimizes SVGs). An empty or missing batch folder is now an error (exit 2).
- `oml setup`: new right-click entries **oml: Convert to ICO** (images) and **oml: Trace to SVG** (raster images; a photo shows the note).
- New regression check `tests/image-check.ps1`.

### Updating existing UI and code from files

- A `styleSheet` replaces the whole sheet. apply now warns when an existing non-empty sheet loses more than half of its characters or drops selectors it had (`styleSheet of screen Showcase replaced: 2737 -> 106 characters, 26 selectors gone (...); the whole sheet is replaced, not merged`), whatever path replaced it (a creation list, `edits.set`, a theme). New `oml describe <module.oml> <Element>... --css` prints only the whole style sheet of a screen, block, email or theme, to edit before a restyle. The edit-existing-flow recipe, `spec.md` and the Copilot file say so.
- A listed existing screen, block, email or theme takes a different `styleSheet`: apply replaces it (a UI change, rule 3) and lists it in the new report field `changed` (`styleSheet of block Card`). CSS that differs only in comments, or in spaces outside quoted strings (around `{ } ; ,`, and around a colon in a declaration), is no change. Spaces inside a string count, and so does a space before a colon in a selector (`div :hover` is not `div:hover`), also inside `@media` and nested rules: a colon is a declaration colon when the next `{`, `;` or `}` after it is not `{`. A screen also takes a different text `title` and new `requiredScripts`. Before, a different styleSheet on a screen or block was refused, and on a theme or email it was ignored silently, so each CSS change needed a full rebuild. A theme listed without `styleSheet` keeps its CSS, and a `baseTheme` is applied (`baseTheme of theme <name>`); a theme `styleSheet` that looks like a path but names no file is refused (before, it was stored as the CSS). `module.styleSheet` is refused with a pointer to themes: an OutSystems 11 module has no style sheet of its own.
- New edit op `replaceWidgets` (`at`, optional `area`, `widgets`): replaces every widget inside a screen, block, email, widget or placeholder; the element at `at` stays. `changed` lists `widgets of <at>`. It is refused before anything changes when a removed widget is used outside the replaced part, naming the widget and where (`NameInput (used by MainFlow/Home/Save/Mark)`). An expression finds a widget by name, so a new widget with the same name and kind keeps such a usage working (a self-test step checks this); a used name given to another kind of widget is refused (`NameInput was an Input, now a Container`). Other references, such as a Label's target widget, are refused with their own message. Two replaceWidgets on one element give one `changed` entry. A Label takes `targetWidget` (a widget name; `""` clears it) in a widget spec and in `set`; `describe` and `tree` show it, and replaceWidgets warns when it removes a Label whose link no new Label restores. A kind change refusal says how to make it on purpose. `oml spec check` knows the op. The entry is one per element, however `at` is written (`Home/Box` and `MainFlow/Home/Box`).
- `changed` also lists each existing element that the apply made public, by any path (creation list, content, `edits.set`): `public of entity Sector`. Before, only a server action made public was reported (as `PublicServerAction`).
- Restated widgets, placeholders and layout of an existing screen are still not applied; the warning now names the op that changes them (`replaceWidgets` with the right `at`, or `addWidgets`). That hint now gives a path that names the screen or block alone (`Screen:Sector` when an entity has the same name).
- `javaScript`, `styleSheet`, `sql`, `expression` and `value` can be `{ "file": "relative/path" }`: the file's text, read as UTF-8 with a BOM removed and nothing else changed (comments stay), relative to the spec file. Several specs and `oml run` steps each read their own files. UTF-16 with a BOM is read too. A missing file, an absolute path or one with `:`, a path that leaves the spec's folder, a link or junction on the way, a folder, a device name, a file over 2 MB, a NUL character and a file value on another key are refused (keys starting with `_` or `$` are notes and are skipped) by apply before the module loads, and reported by `oml spec check`. The JSON Schema accepts the object form. `images`, `scripts`, `resources`, a theme `styleSheet` path, `module.icon`, `copy[].from` and `translations.import` now look for a relative path in the spec's folder first, then in the working folder; a file in both folders with different content gives a warning. A self-test step checks that a React-style file (quotes, backslashes, a template literal, unicode) is stored byte for byte.
- The `edit-existing-flow` recipe also restyles an existing screen (`styleSheet`) and replaces its title widgets (`replaceWidgets`). `oml spec targetWidget` opens the widget section, whose key table now lists a Label's `targetWidget`.

### Preview: scripts and interactions

- `oml preview` runs JavaScript-driven blocks and screens. It loads the module's Script elements (the module's required scripts, the module JavaScript, and the scripts the element and its rendered blocks require, dependencies first) and lists them in `scripts`; a note names the module scripts it did not load. It stubs the client runtime: `$parameters` (node inputs from their arguments, with `--arg` values and defaults), `$actions` (returns a resolved promise), `$public` (FeedbackMessage, Navigation, Security and the rest), `$roles`, a global `controller`, and `$resolve`/`$reject` (the next node waits, at most 2 seconds). Before, code that used `controller` failed with "controller is not defined". The OnInitialize, OnReady and OnRender nodes run in flow order (OnInitialize parent first; OnReady and OnRender blocks first); a node that throws or rejects stops the rest of its action. A flow If whose condition the preview can evaluate (literals and inputs with `=`, `<>`, `not`; not when a value does not match its declared type, texts differ only in case, or an Assign changes the input) follows one branch; another If or a Switch runs every branch and a note names it. A block rendered more than once gets `[n]` in its labels. "OSUI is not defined" and the like get "(not available in the preview; works in the published app)".
- The preview report has `scriptsRan`, `scriptErrors` (`node` and `message`, first 20, repeats once, a node that does not compile once, `errorsTotal` when cut; replaces `javaScriptErrors`), `skipped`, `stubbed` and `console` (first 20, 160 characters each, with `stubbedTotal` and `consoleTotal` when cut), `blocked` and `steps`. The dashboard reads `scriptErrors`.
- No network in the headless preview: a Content-Security-Policy blocks every load and fetch (fetch, XHR, images, fonts, remote scripts and stylesheets, Workers, frames); the runtime cancels navigations (also reloads that page code starts), form submits, `form.submit()`, links with a `target`, `window.open` and `<script type="speculationrules">`; and the browser runs with a proxy that does not exist, no name resolution, no background networking, no pings and no WebRTC outside the proxy. `blocked` lists what was stopped (`file://` and `data:` requests by kind). An Image widget with a remote URL no longer loads it.
- The browser gets 1 s after load plus every `--wait`, 50 ms per step and 2 s per asynchronous node and per `--eval` (at most 60 s), and is stopped 30 s after that; both runs of a screenshot share 150 s. A page that loops forever gives `scriptsRan: false` and a note; a page that did not finish names what was still running. The browser output is read as UTF-8.
- New preview options `--wait <ms>`, `--click <selector>`, `--type <selector>=<text>` and `--eval <js>`, repeatable, run in order after the lifecycle JavaScript and before the screenshot. They also run the browser without `--screenshot`.
- `oml preview --serve` shows a live preview at `http://127.0.0.1:<random port>/` with no key, and reloads it when the module file changes. It serves only that page, to GET requests with a local Host header (HEAD and other methods get 405), never in a frame, and writes no file. Its own live reload passes the navigation guard. In your own browser the page stops the same navigations (none of 31 tested kinds reached the network in Edge), but CSP does not stop navigation and your browser has network access. `--no-open` skips opening the browser. Ctrl+C stops it. It is refused inside `oml run` and the dashboard.
- An Expression widget shows a `+` join only when a part is text: `Count + 1` shows as `{Count + 1}`, not "31".

### Spec: block events, emails, data model and queries

- Block events (Reactive and Mobile). A block declares `events` (name, `mandatory` default true, `inputs`), fires one with the flow node `triggerEvent` (only in the block's own client actions), and a BlockInstance handles them with `"events": { "<Event>": "<action>" }` or `{ "action", "args" }`. A handler input with no arg gets the event input of the same name; any other unmatched handler input is refused. An instance without a handler for a mandatory event is refused, naming the event. Blocks also take `onParametersChanged`. `describe` shows events, `trigger` lines and instance handlers. New recipe `block-popup-event.jsonc` (a confirm popup block and a screen that handles it); the `list-search-paging` recipe and `spec.md` show the OutSystems UI Pagination `OnNavigate` handler (not tested: oml's tests do not use OutSystems UI).
- Reactive emails. `emails` creates an email in a UI flow (default `Emails`) with a required `subject`, `inputs`, `locals`, `widgets` and `styleSheet`. Only the widgets an email allows are accepted (Container, Expression, If, Image, Link, List, TableRecords, Text); others are refused at any depth. Traditional Web modules refuse `emails`. `sendEmail` now works in Reactive server actions: the model API cannot place the node in any action, so oml creates Service Studio's own send action `Send<Email>` once (inputs From, To, CC, BCC and the email's inputs) and the node becomes a call to it. Traditional Web `sendEmail` is unchanged. `oml preview` renders emails; `describe` shows the subject, widgets and Send Email nodes. New recipe `send-email.jsonc`.
- Entities take `indexes` (`name`, `attributes` in column order, `unique`), also on an existing entity (an additive change). New entities also take `identifier` (an attribute that replaces the default `Id`), `autoNumber`, `labelAttribute`, `orderByAttribute`, `isActiveAttribute`, `exposeReadOnly` and `updateBehavior` (`changedAttributes` or `allAttributes`). On an existing entity these options must equal what it has; apply refuses a change, also through `edits.set` (rule 5). Rule 5 now also covers auto number on an existing attribute and the multi-tenant setting of an existing entity. A unique index on an existing entity adds a warning: publish fails if production has duplicate values. On a new entity, an `Id` attribute in the spec sets the type of the default Id (before, it was ignored and listed as existing). `autoNumber` on a non-integer identifier is a problem (the model accepts it, the database cannot number it).
- Aggregates: `groupBy` items can be `{ "attribute", "as" }`. A computed group without `as` gets a valid name (`Year(Order.PlacedOn)` gives `YearPlacedOn`); before, the name was the text after the last dot (`PlacedOn)`). A taken group name is a problem instead of a silent model rename. New keys `groupFilters`, `groupSorts` and `groupCalculated` (after grouping), sort `dynamic`, and `fetch` (`atStart` or `onDemand`) on screen and block aggregates. `cacheInMinutes` (server action aggregates only) and `timeout` were already set through reflection; they are now checked as whole numbers and shown by describe. Group and index names must be ASCII identifiers; a default group name leaves out text literals and accents. Unknown keys in sort, group, join and attribute objects are refused by apply and reported by `spec check`.
- Data actions take `fetch`, `timeout` and `onAfterFetch`; screen and block aggregates take `onAfterFetch` (a screen action of the same screen or block, run after each fetch).
- New edit ops: `addToAggregate` adds sources, joins, filters, sorts, groups and calculated attributes to an existing aggregate; `setArgs` sets arguments of an existing call or navigation by parameter name. Change or remove aggregate parts with `set` and `delete` on their tree paths. Deleting a filter, sort or group of a grouped aggregate can drop its source (11.55.93, no validation error); oml refuses such a delete, and a delete of an aggregate's internal structure. `setArgs` and other `args` accept numbers and true/false.
- Reactive form validation: a client action can set `<Input>.Valid` and `<Input>.ValidationMessage`, and read `<Form>.Valid`. The old note in `spec.md` said this was not possible; it was wrong. The `form-with-validation` recipe now uses this standard pattern (no extra If and Container per input), its server action repeats every client check (name, email, age range), and the UI checklist names the pattern. A new self-test step checks the assignments, the read-only `<Form>.Valid`, and that oml leaves a Button's On Click Built-in Validations at Yes (the default).
- `oml spec check` knows `triggerEvent` (needs `event`), `sendEmail` (needs `email`, `from` and `to`), block `events`, `onParametersChanged` and `emails` (needs `subject`). New self-test step for block events, handlers and Reactive email.
- Add the `aggregate-on-demand-detail` recipe (master-detail with an on-demand detail aggregate), `tests/data-check.ps1`, `tests/data.json` and a self-test step for entity options, indexes, aggregate options, group by and the aggregate edit ops.
- New screens and blocks take `public`, so a block can be made public in the spec that creates it.
- An existing screen or block listed again sets a lifecycle handler (`onParametersChanged`, `onReady`, and so on) that it does not set yet, as `addParts` does; before, this was refused as a changed setting. The report lists each one in a new `changed` array (`onParametersChanged of block Badge -> SetX`). Changing a handler that is set is still refused (use `set`). On an existing Traditional Web screen or block, lifecycle keys and events are refused as when it is created (before, they were ignored without a word). `spec.md` shows how to re-run an action when a block input changes.

### Production rules

- Rule 4 (public signatures) is precise: no type change, no new mandatory input, no input made mandatory; no input change at all on a public Reactive or Mobile block or screen; an optional input (or making an input optional) is safe only on public server and service actions and Traditional Web blocks and screens; a new output is safe only on public server and service actions. Rule 3 (no renames or deletes) is unchanged.
- Rules: an existing block's events are contract elements (rule 3: no rename, no delete). A new event on an existing public block, a new mandatory event on any existing block, and making an existing event mandatory are refused (rule 4). The send action `Send<Email>` that oml creates is not public.
- Fixed: listing an existing entity, structure or static entity in a spec without `public` made it private, because a missing `public` meant false (1.3.0 and earlier). Consumers in other modules then broke after publish. Now a missing `public` keeps the element's own setting (also for actions and content files), and apply refuses making an existing public element private, through spec keys and `edits.set` (rule 4).
- Rule 4 is enforced for inputs and outputs on every path (creation lists, `addVariables`, `addParts`, `set`): on an existing public element apply refuses a new mandatory input, an input made mandatory, a type change, any input change on a public client action or a public Reactive or Mobile block or screen, a new output except on server and service actions, and a type change of an event input on a public block. Before, a listed public action could get a new mandatory input. Making an input optional stays allowed on server and service actions and Traditional Web blocks and screens.
- Rule 7: only a server action that becomes public needs the user's OK. Apply allows it, new or existing (private to public, through spec keys and `edits.set`), and adds a `PublicServerAction` entry to `newWarnings` with the hint "Ask the user. If they say no, remove `public` from the spec and apply again from the same source." More than 12 such server actions are named in one message. Every other element (entities, structures, static entities, blocks, screens, client actions, roles, and so on) may become public with no warning. Service actions get no warning, because other modules call them by design; exposed REST methods have no public setting. Public to private on an existing element stays refused (rule 4), now for every kind with a public setting: images, scripts, resources, themes and process activities too (before, an existing public image, script, resource or theme could be made private with `edits.set`). Images, scripts and resources listed again take `"public": true`. A block made public in the same spec may get a new optional event: rule 4 holds for blocks that were public before the apply. Rules 4 and 7 read word for word the same in `rules.md`, the Copilot instructions and the website; the README sums them up. Only `entity-with-crud` keeps public server actions; the other recipes keep them private, and recipes without a caller for them report `UnusedUserAction`. The `unused-action` fix in `oml check` says to ask the user before making an action public.
- A name the model would rename (a "name taken" problem) now names the element that holds it: kind, owner and a path that `describe`, `tree` and `edits` accept (checked by the write rules of element paths), for example `name taken by input parameter Status of block LatticeLoader (path MainFlow/LatticeLoader/Status)`. Before, the message said "by a generated CRUD action or another element". This covers creation lists, `addParts`, `rename` edits, `copy`, content files, static entities and their attributes, indexes, aggregate groups, REST integrations, references and aliases, emails, extensions, flow nodes, UI flows and exception handlers. A clash names a referenced element rather than a flow node that calls it, and a variable's problem names it after the label (`block LatticeLoader: local Status: name taken by ...`).
- A unique index on an existing entity is now a `UniqueIndexOnExistingEntity` entry in `newWarnings` (it was in `warnings`), so the agent explains it to the user.

### Speed

- Add `--timings`: a command that loads a module (`apply`, `inspect`, `describe`, `validate`, `install`, `new`, `census`, `tree`, `find`, `preview`, `openapi`, `architecture`, `check`) adds a `timings` object with milliseconds per phase (`startup`, `serviceStudioInit`, `load`, `rules snapshot`, `save scratch`, `build logic`, `save`, `reopen`, `json`, ...). `oml run --timings` adds it to every step. The commands that run without Service Studio (`spec`, `doc`, `lt`, `doctor`, ...) refuse it with exit 2. Without the option the output does not change. `skill/reference/commands.md` lists the phases.
- `apply` skips the scratch save and reload of the data model when the spec has only logic keys (actions, blocks, screens, edits, REST, timers, processes, variables, system events, emails, locales, translations, folders, `tidyFlows`). The data phase then changes nothing, so the reload gave the same model. It saved 1.3 to 1.7 s per apply on the measured modules (the reload, and the slow first read of the reloaded model in flow layout). A spec with any data key reloads as before.
- In `oml run`, `apply` takes the module that an earlier step left open (same file, not changed on disk) instead of loading it again, when the file has the same write time, length and SHA-256 as when it was loaded. The module leaves the cache, so a later step that reads the source loads the file again. The scratch module of the data phase is now closed at the end of the apply; before, it stayed open for the rest of an `oml run` or a dashboard session.
- `install` loads the staged file once. It writes the validated bytes to the target and checks the target's SHA-256 against them, instead of loading the same bytes a second time (0.4 to 0.8 s on the measured modules). A read-only target is refused before the backup. A write that fails and leaves the target unchanged (a file another program holds open) says `Nothing installed` and keeps the backup; a write that changed the target restores the backup and says so.
- Reflection lookups (element names, properties, methods, widget and node types) are cached per type. A from-scratch build of 150 entities with 300 server actions, 300 screens and 51 blocks was about 4 s faster in the first measurement (29.9 s to 25.6 s); later runs on a busier machine showed 32.2 s to 29.9 s.
- The launcher runs without dynamic PGO (`TieredPGO` false): every command is a short process, so it only added JIT work. Measured 7 to 18 percent faster per command.
- Measured on the biggest real module found (2.3 MB `.oml`) and a synthetic module (2.8 MB, 41,000 objects), lowest of 3 runs, same machine. Apply with logic only: 5.6 s to 4.4 s (real), 8.2 s to 5.8 s (synthetic). Apply with data and logic: 6.1 s to 5.3 s, 8.4 s to 7.5 s. Install: 2.9 s to 2.4 s, 3.6 s to 2.7 s. An `oml run` of inspect, describe, apply, validate and apply on the synthetic module: 13.9 s to 9.0 s. About 1.5 to 2 s of every command is Service Studio's own start-up (`serviceStudioInit`), which oml cannot shorten; `oml run` pays it once.

### Fixes

- Fixed: the first model command on a Service Studio build not checked yet (after an update or a first install) never ended. It printed `running self-test...`, then used more and more memory. The self-test's `oml run` step started the self-test again inside itself, without end (1.2.0 and 1.3.0). The self-test now runs once. It also has a time limit of 10 minutes: past it, oml stops with exit 2 and an error that says what to do, instead of waiting forever. In `oml dashboard` the limit fails the command with that error instead, and the dashboard refuses model commands until it is restarted, so a page stays served.
- Fixed: JSON output lost or broke non-ASCII text. oml wrote stdout in the console code page (often 437 or 1252), so curly quotes in module text (such as the OutSystemsUI Licenses block) became a plain `"` and made the JSON invalid, and other characters (Georgian, many accents) became `?`. JSON on stdout is now pure ASCII (`\uXXXX` for every character above U+007F): valid and lossless in every shell and code page. `--pretty` in a console window shows the real characters. A console window gets UTF-16 text, and redirected text output is UTF-8. `oml run -` reads stdin as UTF-8. oml's own text (usage, `oml doc`, `oml spec`) is pure ASCII. See "Output encoding" in `commands.md`.
- Fixed: a spec string with a lone surrogate escape (such as `\uD800` without its pair) ended `oml apply` with an unhandled .NET exception. `apply`, `spec check` and `oml run` now report it as a problem with its path.
- Fixed: the `owner` of a sample in `newWarnings` was missing in a standalone `apply` (it was read after the reopened module was closed). It now shows, as it did inside `oml run`.
- Fixed: `apply` with a spec file that does not exist crashed with a .NET error; it is now a usage error (exit 2) that names the file.
- Fixed: `describe X` failed with "ambiguous path 'X' at 'X'" when a screen, block, flow or nested element had the same name as another element, also when only one of them was this module's own top-level element (for example a screen `Login` and the `(System)` action `Login`). This module's own top-level element now wins, then a referenced element, then the shallowest nested one. A path that is still ambiguous lists every candidate with its kind and an exact path that works in `describe`, `tree` and `edits` (`Screen:Sector, ServerEntity:Sector`). See "Element paths" in `commands.md`.
- Paths that used to resolve silently by depth are now refused as ambiguous, with every candidate listed: an entity and a screen of the same name, a flow and a screen, a block and a screen, a server and a client action of one reference (`(System).ListSort`). A first part that matches this module's own top-level element no longer falls through to a nested or referenced element when that element lacks the rest of the path: `Dashboard/Title` with a screen `Dashboard` fails instead of changing `Home/Dashboard/Title`, and `Customer/Name` with a screen `Customer` no longer reaches the referenced entity's attribute. `edits` refuse elements of referenced modules. A path that changes the module (`edits`, `folders`, `tidyFlows`, `globalExceptionHandler`) must name each part exactly: `Save/Note` is refused when two actions are named Save, even if only one has Note, with the paths of both.
- Fixed: `Kind[i]` paths of flow nodes, switch conditions and action or block instance arguments, `tree` child order, and `describe`'s order of exception handlers changed between loads of the same module. They now follow a fixed order (conditions in their order, arguments in parameter order, other nodes by their key).
- Fixed: `describe --history` of a `(System)` structure (such as `Attachment`) failed with "Operation is not valid due to the current state of the object", and of the `Registered` or `Anonymous` role with "The method or operation is not implemented". These elements keep no history; they now get none.
- Fixed: `inspect` of a Service module ended with a .NET stack trace (the module JavaScript getter throws there).
- Fixed: `describe` of a referenced block or script failed with "Specified method is not supported", and `tree` of one ended with a stack trace. A referenced element's body is not read now.
- Fixed: a file that is not a module ended every command with a stack trace. It is now `{"error": "Cannot read <file>: it is not a valid .oml module (...)."}` with exit 2.
- Readers print what they can read: `describe`, `inspect`, `tree`, `find` and `census` leave out a part the model cannot read (a widget, node, property, row or reference) and list it in `"unreadable": [{"part", "reason"}]` instead of failing the command.
- Fixed: `inspect` listed elements in a different order on each load of the same module (content images, scripts and folders, blocks, screens, site properties, actions, and the rest). Every list is now sorted by name (ignoring case), so the output is the same on every load. This changes the order of the lists, not their content.
- Fixed: `install` of a file that is not a module ended with a stack trace, and `oml run` and the dashboard showed a raw .NET error for it. All now say `Cannot read <file>: it is not a valid .oml module (...)` with exit 2.
- Fixed: when `replaceWidgets` was refused because a removed widget is used in an unnamed widget, the "used by" path did not resolve, or named another widget. It is now a path that `tree` and `edits` read as that widget (`Home2/Container[1]/Container[0]/Expression[0]`). Element paths also find unnamed widgets under unnamed containers.
- Fixed: a name taken by a widget of the same screen or block gave the "not found by oml" message; it now names the widget and its screen (`name taken by input NameInput of screen Home (path MainFlow/Home/Box/NameInput)`).
- Fixed: a new warning whose id and message match a warning the source already had (for example a second `UnusedUserAction`) could show the old element in its samples. New warnings are now told apart by their detail too.
- `describe` lists action and screen parameters in model order (the order Service Studio shows; a function is called by position), not by name. This changes `describe` output for elements whose parameters are not in name order.
- Fixed: a known command with missing arguments (`oml describe`) printed the whole usage; it now prints that command's lines.
- `oml dashboard`: after a self-test past its limit, every later command is refused before it touches the model, also the launcher commands (`doctor`, `spec`, ...).
- Fixed: `"mandatory": false` on an input (actions, screens, blocks, block events, emails) was ignored, so every input was mandatory. An explicit `true` or `false` is now set. Without the key, an input stays mandatory, the model default, as before; `spec.md` said the default was false, which was wrong. The detail template's `<Entity>Id` input is now optional, as documented.
- Fixed: a screen or email whose UI flow name was taken (for example by a referenced module's `MainFlow`) was created in a renamed flow (`MainFlow2`) while the report said `flow MainFlow`. Apply now refuses it and names the free-name fix.
- Fixed: a widget, node or handler argument that is not a string, number or true/false (`"Id": [5]`) now gets a clear message instead of a .NET error. A number or true/false is used as the expression (`"Id": 5` is `5`). `events` on a widget that is not a BlockInstance is refused instead of ignored.
- Fixed: a delete edit that the model fails on (for example a source, or an aggregate attribute a group sort uses) ended `oml apply` with no JSON report. Any model failure in a build step is now a problem in the report.
- Fixed: an existing element listed in a creation list ignored changed values without a word (a new block event was dropped, `public` or a new attribute length did nothing). Now new parts are added under the same rules as `addParts` and `addVariables` (attributes, static records, action and screen inputs, outputs and locals, screen actions, aggregates, data actions, block events, REST methods; parts added to an existing screen are listed in `created`), and a setting the spec gives that differs from the module is a problem that names the key and the edit op to use (also for roles, site properties, timers, REST methods and client and session variables). Expressions are compared without case and spaces outside text literals; style sheets after comments and spaces are removed; screen access after the roles the model adds by itself. An existing flow is compared by node names and count (comments and the model's unnamed nodes do not count). A restated screen or block aggregate is compared by sources, `maxRecords`, `fetch`, `timeout` and `onAfterFetch`; a new input of an existing event is added. Widgets, placeholders, layout and processes are not compared: `warnings` names them and the op that changes them. UI settings (`styleSheet`, a text `title`, `requiredScripts`), unset lifecycle handlers and `public` are applied instead, as described above. A `systemEvents` entry that already calls the same action is reused. A creation-list spec applied again on its own result saves and changes nothing; `tests/reapply-check.ps1` checks this for every fixture and recipe.
- Fixed: `oml check` named a Refresh Data node in `server-call-in-client-event` as an empty name; it now says `Refresh <source>`.
- Fixed: `oml <command> --help` printed the whole usage; it now prints that command's lines (`oml check --help`), also for the commands that run without Service Studio (`lt`, with one line per subcommand, `font`, `doctor`, `setup`, `image`, `dashboard`).
- Fixed: `oml spec dataActions` opened Traditional Web UI. `dataActions`, `aggregates`, `locals`, `inputs`, `dynamic`, `unique` and `index` now open their sections.
