## Unreleased

### Added

- **Warm workers: model commands from a shell take about 0.1 s instead of 2 to 5.** `inspect`, `describe`, `find`, `query`, `tree`, `flow`, `export`, `openapi`, `validate`, `check`, `architecture`, `review`, `apply`, `new`, `batch`, `spec check`, `test bdd` and `test scenarios` go to a background oml process that keeps Service Studio's model loaded and the modules it read open (a changed file loads again). Same stdout, stderr and exit code as before; a pool of `performance.warmWorkers` (default 2), and a command that finds every worker busy runs on its own, so parallel agents never wait. Workers stop after `performance.warmIdleMinutes` (default 20) and belong to one oml and one Service Studio build; they run from a copy of oml's files, so a rebuild is never blocked. `oml mcp`, and so `oml code`, sends its calls to the workers too: a program with an oml call takes about 0.3 s instead of 5. Anything wrong on the warm path runs the command cold. `performance.warm false` turns it off; hidden `oml warm status|stop` shows and stops them; `oml doctor` names them. New setting kind `number` (with a range) in the project config. `tests/warm-check.ps1` compares 23 commands warm and cold byte for byte; the rest of the suite runs cold (`OML_WARM=0`).

- **Generic model operations in `edits`: `add`, `remove`, `move`, and `set` with `type`.** A spec reaches any Model API object by type and member name, checked against the installed Service Studio by reflection. `add` makes a child with the parent's `Create*` method (`"parent": "Customer", "type": "IEntityAttribute", "name": "Code", "first": true, "properties": {...}`); `remove` takes out only what the same spec made; `move` reorders attributes, parameters, widgets and records (`before`, `after`, `first`, `last`). `oml spec check` resolves the type and checks each key and value without a module; unknown types, members and enum values name the closest ones. The production rules hold for every operation, and after the build apply also runs the before/after check of `oml review` (rules 2 to 6 refuse the save). `oml spec add`.
- **`set` takes more values:** decimal and long numbers, ISO date-times, and `{ "element": "<path>" }` for an element without a name of its own; and widget events (`"onClick": "<screen action or screen>"`) on existing widgets.
- **(System) server actions a module does not reference yet** (ListAppend, ListClear, ListInsert, ListRemove, LogMessage, CommitTransaction, ...) work in server flows: oml adds them from Service Studio's tutorial module and says so in `warnings`. A client flow is refused with the steps (Service Studio adds (System) client actions).
- **`oml model-coverage --out <folder>` (maintainers):** the Model API coverage map in tests/model-api (every member reachable from IESpace: covered by which key, read-only, rule, out of scope, or not covered and why), generated from oml's own IL and the rule tables, to diff on a new Service Studio build.
- **Frontend skills for OutSystems UI work (`skill/frontend`, `oml doc frontend`):** the 16 interface skills of jakubkrehel/skills (MIT), remade for OutSystems 11 Reactive and Traditional Web. Design rules: `better-interface` (one ranked review), `better-accessibility`, `better-layout`, `better-writing`, `better-typography`, `better-colors`, `better-ui`, `better-motion` and `build-design`, written as theme CSS, widget properties and attributes and OutSystems UI patterns. Workflows the user asks for: `interface-review` (a staged copy against its source), `explain-interface`, `break` and `variant` (previews injected with `oml browser try`), `state-machine` (a test screen in a staged copy), `afk` (staged copies and review files, never an install or publish) and `upskill` (team rules, hooks, checks and settings from session history and oml's logs). `oml doc <name>` prints one (`<name>/<file>` a linked file); `oml doc --search` adds the best matching skill after its doc hits, so the doc ranking is unchanged; `oml doc ui-checklist` points to them.
- **The official OutSystems skill's examples as specs:** tests/model-ops/examples.md lists each example with the spec that does it; tests/model-ops-check.ps1 applies all of them. Recipe `attribute-position-reorder`.

### Changed

- **New production rules: agents change existing elements in place instead of duplicating them.** `oml apply` compares the result with the source module by key and has three outcomes. **Always refused** (rule 2, with any flag or setting): deleting an existing entity (regular or static) or attribute, changing an attribute's data type, renaming an attribute, an entity deleted and made again with a new key, and a `copy` that holds an entity (a new, empty table; `oml migrate` keeps entities in the old module, so it is not affected). **Saved only with the user's yes**: deleting any other existing element (rule 3: actions, screens, blocks, structures and their attributes, static records, parameters, events, roles, exceptions, site properties, timers, REST methods, processes), and changes that can lose data (rule 5: a shorter length, fewer decimals, a new mandatory setting or an auto number change on an existing attribute, a new identifier or multi-tenant setting; rule 6: new or changed SQL with `DELETE`, `UPDATE`, `MERGE`, `TRUNCATE`, `DROP`, `ALTER`). Without the yes apply saves nothing and reports `needsApproval: [{kind: "delete"|"data", element, what}]`, a `next` that says to ask the user, and exit 1. **`oml apply --user-approved`** saves them and lists each in `approved`; the project profile's `autoApprove.deletes` and `autoApprove.dataDeletion` save each kind without the flag. In `oml mcp` and `oml code`, `apply --user-approved` is a gated call. **Saved and reported**: renames and edits of existing actions, screens, blocks, structures and entities, entity settings (label, order by, is active, update behavior, expose read only), a longer length, optional, and every signature change of a public element (renamed, made private, inputs, outputs and events added, removed or retyped, made mandatory): apply and `oml review` list each one in `breaking` with what the consuming modules must do (refresh references, fix callers). Security changes stay warnings (rule 7). Creation lists now set an existing attribute's length, decimals and mandatory setting, an input's type and an event's mandatory setting as the spec says, and `edits.remove` takes existing elements under the same rules. `allowDataLoss` is no longer needed. skill/rules.md, SKILL.md, the spec and command references, README, oml-full.md and the website say the new rules; tests/rules-check.ps1, tests/model-ops, the self-test and the data, public and reuse checks test each outcome.

### Fixed

- The Dropdown keys in `oml spec`: `labels` and `values`, written on one item of the list (`Status.Label`), not `optionsText` and `optionsValue`.

## 1.23.0

Traditional Web to Reactive, prepared by code, and an interactive menu for people.

### Added

- **Newer Service Studio builds, and `oml studio open <Module>`.** From Service Studio 11.55.98.65437 the open-module list is `listOpenModules`, not `listApps` (which those builds no longer have); oml reads the server's tool list and uses whichever it has, so `pull`, `publish`, `references`, `query --live`, `studio` and `studio close` keep working. `oml studio` also prints the server's own line (`server`: "Service Studio <version>, MCP contract <N>.") and `canOpen`. `oml studio open <Module> [--environment <host>]` finds the module on the environment Service Studio is logged in to (`searchApps`) and opens it in a new tab (`openModule`, Service Studio 11.55.99.65452+), waiting while Studio downloads it; unknown and ambiguous names refuse, older builds refuse with the manual step. It is a gated call in `oml mcp` and `oml code`. A `MODULE_AMBIGUOUS` or `ENVIRONMENT_REQUIRED` answer comes with what to do. `tests/studio-check.ps1` covers both kinds of build against a mock, taken from the official skill's description (OutSystems/outsystems11-mcp, 8cdd94f).
- **`oml mcp`: an MCP server on stdio, so Service Studio loads once for many calls.** An agent's MCP client starts `oml mcp` once and calls three tools, `read`, `write` and `gated`; each takes `{"args": [...]}`, an oml command line. The commands run in the server's process, so the model and the self-test load once: an `inspect` takes milliseconds instead of about 2 s, and a module that a command only reads stays open for the next call (a file that changed on disk is read again). A result is `{"exit", "output", "stderr"}` with the command's own JSON; `isError` is true only when oml refused the call, such as a command in the wrong tool (the refusal names the right one) or a `batch` through `read` with a step that writes. Which tool runs which command is one table in the code (`oml commands` shows it as `mcp`). Calls that arrive together are all answered: commands in the process run one at a time, while gated commands, `browser` and `doctor` run in a child oml process next to them. `server` and `review --server` read the OML_SERVER_* variables from the person's Windows user variables when the client did not pass them. `tests/mcp-check.ps1` covers the protocol, the tools, the refusals and the speed.
- **`oml code`: code mode for oml, one Python program for many oml calls.** `oml code run --json -f <program.py>` runs a program that calls oml through three tools, `oml.read`, `oml.write` and `oml.gated` (each takes the command line as a list), in parallel where it can, and returns only its last expression; `helpers.oml` parses the output (`oml.read("inspect", "A.oml")`, `oml.many([...])`). Reads and writes run; a gated call (install, publish, references, pull, lifetime, server) pauses the program (exit 3) until the user runs `oml code approve <id>` in their own terminal, and all calls pending together are approved together. The runtime is a copy of the standalone code-mode runtime in `codemode/` (standard library only, unchanged), shipped beside `bin/`; oml finds Python 3.9+ through `OML_PYTHON`, `py -3`, `python` or `python3`, or says what to install. oml writes the config on every run: its `oml mcp` server as the `oml` connector, started in the project root with oml's own variables as `${NAME}` references, `oml.read` and `oml.write` allowed, `oml.gated` asking; the project's `.oml/codemode.json` adds connectors (a task board), rules and limits (`oml code init` writes it from `.mcp.json`). Every runtime command is there: `get`, `wait`, `cancel`, `reject`, `doctor`, `prompt` and `instructions` (written for small models), `serve` (an MCP server with one tool, `execute`) and the rest. `approve` refuses NUL as stdin too: on Windows Python's `isatty()` is true for it, so an agent's `approve < /dev/null` got through. The skill says when to use it (`oml doc commands#code-mode`); `oml create` ignores `.oml/codemode/` and `.oml/code/`. `tests/code-check.ps1` covers it and skips without Python.
- **Questions and colour for people.** `oml create`, `hooks install`, `config set`, `team-rules add` and `studio open`, run by a person without the argument they need, ask for it and show the command it stands for; agents are never asked. The readable view colours what passed, needs a look or failed, and oml commands; `output.color` in the config (auto, always, never).
- **Test accounts by role.** `.oml/test-accounts.local.json` (written by `oml create`, kept out of git) holds the app's test accounts; browser scripts log in with `{"login": "<role>"}` or `$account:<role>.password`, oml types the password and never prints it, `oml browser accounts` lists the roles, the profile names them, and the hook keeps agents out of the file.
- **`oml code` runs code-mode 0.3.1.** Programs get `project_root` (a program runs in an empty folder of its own: `open(project_root + "/path")`) and `parallel(..., on_error="return")`. `oml code approve <id> --same-tool` or `--all-remaining` lets later calls of one execution run without another pause (deny rules still win; it ends with the execution and is logged). `.oml/codemode.json` takes `guidance` (the project's words for its agents, added to the `execute` tool and the instructions) and `work_dir`. oml now uses the runtime's own settings for its hints (`CODEMODE_COMMAND`, so a detached program prints `oml code` hints too), the programs folder and `oml code init`, instead of replacing its functions; the runtime's console check on Windows replaces oml's.
- **`oml server pull --app`, `oml review --server` and `oml server check`: whole applications, server versions and an end-of-day score.** `oml server pull --app <Name> --out <folder>` saves the published version of every module of an application, with one login. It never overwrites a file: the folder's `oml-server.json` records each file's module key, version id and hash, so a second pull lists the same version as `unchanged` and downloads nothing, and any other file is skipped with the reason. An unknown application name lists the closest names. `oml review --server <Module> <v1> <v2>` pulls two versions (a number from `oml server versions`, `published` or `latest`) into a temporary folder, or `--keep <folder>`, and runs the normal review between them; the output adds `server` with both versions and who uploaded them. `oml server check [--app <Name>]...` keeps the published modules in a cache per host (`%LOCALAPPDATA%\oml-cli\server-cache`; a module is downloaded again only when its published version changed), runs `oml check` over them with the last run as the baseline, and appends one line per run to `history.jsonl`. It prints a summary first: the environment score, each module's score and its change since the last run (`worse`, `new`, `better`, `same`), and the modules published since then; the findings are in the HTML report. It is not scheduled: agents run it when the user says "that's it for today", with `oml memory dream`, when `OML_SERVER_HOST` is set. The docs now spell out the way back: pull, `oml apply`, then the person opens the staged file in Service Studio and publishes it (or `oml publish` while Studio is open); oml never publishes through the REST API, and a publish in between means pull again. `tests/server-check.ps1` covers all three against the local mock, which now serves real modules.
- **`oml memory dream`: an end-of-day tidy of the project memory.** Work laptops are off at night, so it runs when the user ends the day: the user says "that's it for today", and the agent runs `oml memory dream --prepare`, distills the packet and runs `--import`. `--prepare` writes `instructions.md` and `packet.md`: the records added since the last dream, records whose elements are no longer in their module, failures that repeat in the usage log, records that did not help, and duplicate, near-duplicate or contradicting pairs. The agent answers with a JSON list of add and retract operations. `--import` writes only the operations that pass the checks (the id exists and is live, not a duplicate, the elements exist, no secret, the limits of `add`), prints the rejected ones with a reason, and records the dream so the next packet starts there. `--status` shows the last dream and what changed since. `recall` and `handoff` print `endOfDay` once a day, so the agent tells the user about the phrase. The skill names the trigger phrases. Some `oml memory` usage lines are shorter, so `oml help --all` stays within its budget.
- **`oml browser start --attach [<port> | <ws url>]`: test in your own Chrome, where you are logged in.** An app behind SSO or MFA can now be tested without storing a password. Start Chrome with `--remote-debugging-port=9222 --user-data-dir=<a separate profile folder>` (Chrome 136 and later refuse remote debugging on the default profile), log in there once, and attach. oml reads `/json/version` on 127.0.0.1 only and refuses any other host, opens one new tab, works only there and closes only that tab; `oml browser stop` detaches and your browser and tabs stay open. `--attach` on `browser run`, `page` and the other page commands attaches for that one command. While attached, oml acts as you in that browser.
- **A `handoff` step: a person logs in, then the run goes on.** `{ "handoff": "log in", "until": { "url": "/Home" }, "timeout": 300000 }` brings the window to the front, prints one `attention` line on stderr and waits until `until` holds (the URL contains a text, or a target is `visible`) or, at a terminal, until Enter is pressed. A run in a session sends the attention line and the Enter through the session to the terminal that ran it. An agent's run has no terminal, so it needs `until`; without one the step is refused with what to add. A handoff needs a visible window (`--headed` or `--attach`). A step that fails on a screen with a password field gets a `hint` on how to get past the login, and `browser page` reports it as `login`; oml does not pause on its own.
- **`oml browser raw <CDP method> [<params json>]` and a `raw` step: any Chrome DevTools Protocol call on the session's page.** It prints `{ method, result }` (a result over 20,000 characters goes to a file) and needs `oml browser start` or `--attach`. `Browser.close` and `Browser.crash` are refused; while attached, so are `Target.*` calls on tabs that are not oml's and clearing storage, cookies or cache, since they would act on your real browser.
- **`oml query <module.oml> "<ModelQL>"`: read-only questions on the model graph.** It runs Service Studio's ModelQL engine through `oml-tool.exe`, so Service Studio may be closed: `Root { Entities { Name Attributes { Name } } }`, `AllDescendants(ofType: "IMobileScreen") { Name }`, a list's `(name: "X")` or `@filter`. `--fields <Type>` lists a type's fields. Lists are cut to `--limit` (default 50) and the result to `--max-chars` (default 20000), and a cut says where. A refused query passes the engine's message through with a `next` hint. A `@filter` condition is compiled as C# by the engine, so oml allows only `_`, its properties, literals, comparisons and a few string methods, and refuses the rest before anything runs. `--live` asks Service Studio's MCP `runQuery` on the open module (not yet tested live). It is a step of `oml batch`.

- **A Combo Box with a Source Entity becomes a Dropdown over an aggregate of it.** The screen translator builds the aggregate `Get<Entity>Options` (a static entity's active records by its order attribute, another entity by its label attribute), with the entity's identifier as Options Value and its label attribute, or the Source Attribute, as Options Text; a Combo Box on a record list gets its entity's identifier as the value. `oml export` and `oml describe` now read a Traditional Combo Box's source record list, Source Entity, Source Attribute and Special List, `oml apply` sets `sourceEntity` and `sourceAttribute` on one, and `oml inspect` lists an entity's `labelAttribute`, `orderByAttribute`, `isActiveAttribute` and an `identifier` other than Id. A special list stays a Todo. A static entity's aggregate fetches all its records (Max Records is its record count); another entity's keeps the default 50, with a Todo to raise it, since the Traditional Combo Box showed every record.

- **`oml migrate plan` and `oml migrate status`.** `plan` reads a Traditional Web module and writes, into a new folder, a plan, a spec for the old module (entities, static entities and roles made public, plus a public wrapper action for each entity action the copied logic calls), a spec that re-points the logic to the wrappers in a working copy of the old module (`repoint` edits, before the copy, where the entity actions and wrappers are both local), a spec for the new Reactive module (references from producer files found with `--in`, then the `copy` from that working copy) and a worklist of screens and blocks with their descriptions. It changes no module. `status` compares old and new by name and shows the progress and the timers and processes that now exist in both. The plan also exports every screen, web block and email (`oml export`, one `oml batch` call) and translates them by code into `4-screens.json` (client variables, blocks, screens, applied after the new module spec), with `4-screens.md` listing per element what is translated, partial or left, as checkboxes; the entity actions the screens call get wrappers too. Session variables used only by screens and blocks, with a basic type and a harmless name, become client variables; the others are `manual`, with the reason. `--template <reactive.oml>` picks the layout block and its placeholders; `css/` holds the style sheets (theme sheets are ported by hand). SOAP and integration elements are copied, entry points and other content are listed by kind, and `status --plan <folder>` reports the screens by status. `oml doc traditional-to-reactive` starts with this flow.
- **`oml export <module.oml> <Element>...` and `otherContent` in `oml inspect`.** `export` prints a screen, web block or email as JSON (kind, inputs, locals, access, style sheet, actions and Preparation as spec-format flows, the widget tree with its properties) for tools such as `oml migrate`; read an element with `describe` instead. It is a step of `oml batch`. `inspect` lists every module element that no other section lists (consumed SOAP references, emails, entry points, web services) in `otherContent`.
- **`oml menu`: an interactive menu for people.** Tasks in groups (start, project settings, module, application, agents, docs, assets, every command) with a one-line description each; arrows or `j`/`k`, Enter, type to filter, Esc back, `q` quit. It shows the exact command line before it runs the task, with the human view of the output, and has a file picker and an editor for the project profile. A bare `oml` opens it only at a real terminal (input and output not redirected, `OML_OUTPUT` not `json`, `OML_MENU` not `0`, no agent or CI variable); everywhere else a bare `oml` prints the overview and every command behaves as before. Tasks that need a yes from a person are not in it.
- **`repoint` edit.** `{ "op": "repoint", "element": "<Execute node path>", "action": "<Name or Module.Name>" }` makes an existing call node run another action. The node keeps its place, name and key, so what reads its outputs stays valid. Arguments are set again by parameter name; an argument without a matching input, or a mandatory input without an argument, is refused. A node that already calls the action is not changed.
- **Widget keys documented, and two reader additions.** `skill/reference/spec.md` now lists the widget keys that set a model property by its name: `confirmationMessage` and `isDefault` (Button, Link; Traditional Web too), `icon` (Icon), `inputType`, `prompt` and `maxLength` (Input), `showPopup` (Popup), and the image size as `attributes.width` and `attributes.height`, with what has no key (an external URL target, a Radio Group, an image URL source, a column sort, a Dropdown's empty value, a Reactive screen's own JavaScript) and what to use instead. `oml export` adds `_targets` to a flow node the spec cannot express: the elements its properties point at, by name (the widgets an Ajax Refresh node refreshes). `oml inspect` gives each session variable its `default`.
- **Author on what oml creates or changes.** Service Studio showed "Created by Unknown" for everything oml made. The project profile has `author` (`oml config set author "Ana Silva"`; one line, at most 100 characters; empty clears it), and the `OML_AUTHOR` variable wins over it. `oml apply` (also the elements a `copy` pastes) and `oml new` write it as `CreatedBy` on what the run created and `LastModifiedBy` with `LastModifiedDate` (the local time) on what it created or changed, found as `oml review` finds changes; nothing else is touched. The apply report gains `author`; on a Service Studio build whose history fields are read-only, one line in `warnings` says the name could not be written. Without an author the apply still saves, and its `next` says to ask the user for a name; the profile tells agents to ask before the first change. `oml create --author "<name>"` writes it into the new project.
- **Import a Swagger or OpenAPI file as a consumed REST API.** `{ "restClients": [{ "name": "Petstore", "openapi": "petstore.json" }] }` gives a new consumed API every method, path, query, header and body parameter, request and response structure (nested objects, arrays) and enum of a Swagger 2.0 or OpenAPI 3 JSON file next to the spec. It runs Service Studio's own importer in oml's process, so the result is what Studio's "Add all methods" would make. Nothing is fetched (Studio's favicon lookup is skipped); a `$ref` to another file or a YAML file is refused with what to do. What Studio cannot import (an API key or other security scheme, an element with several types) is listed in `warnings`. `baseUrl` and `actions` in the same entry apply after the import; a later apply does not import the file again.
- **`oml review --prepare <folder>` and `--import <findings.json>`: a blind logic review by an agent.** oml finds no logic bugs and runs no model, so `--prepare` writes a small packet for a reviewer subagent: `instructions.md` (what to look for and the exact JSON answer format) and `changes.md` (each changed or added flow as `describe` text, its steps with element paths, the changed lines, and each changed expression before and after). It holds none of oml's own findings, and the same modules give the same packet. `--import` checks the reviewer's answer: a finding whose path is not in the new module, with no evidence, or with evidence that is not text of the element it names is rejected with the reason. The accepted ones print in the shape of oml review's findings (rule `logic-review`), merged with oml's new findings, with a summary of accepted and rejected.
- **JavaScript syntax check in `oml validate` and `oml apply`.** Headless validation never checks JavaScript: Service Studio's editor does, so a module built by oml could hold JavaScript that breaks only in Studio or at publish. oml now compiles every JavaScript node (as the body of an async function, as the platform wraps it, so `return`, `await`, `$parameters`, `$actions` and `$resolve` parse), Script, and module or Traditional Web screen JavaScript with the `node.exe` that ships with Service Studio, in one process, without running anything. Each syntax error is an error with id `JavaScriptSyntax`, its element path, the line and column in the stored text and node's message. `apply` checks only the JavaScript it adds or changes, reports an error in `newErrors` and does not save. Without `node.exe` the check is skipped with a `note` (validate) or a line in `warnings` (apply). It adds about 0.5 s to `validate` on a big module and little to `apply`.
- **`oml server modules`, `oml server versions` and `oml server pull`: any module and any version from the platform server, with Service Studio closed.** Until now oml saw only the modules open in Service Studio, and `oml pull` needed a person's approval. `oml server` logs in to the server's REST API (`server.api/v1`) as Service Studio does (a password login, client `service_studio`), with `OML_SERVER_HOST`, `OML_SERVER_USER` and `OML_SERVER_PASSWORD` from the environment. `modules` lists every module with its key, application and last version (`--app` keeps one application); `versions <Module>` lists its versions, the published one marked; `pull <Module> [--version N] --out <file.oml>` saves one version (default: the published one) and never overwrites a file. It reads the server's flags first; a server without the REST route gets `noRestRoute: true` and the advice to open the module in Service Studio and use `oml pull`. REST only, no SOAP. HTTPS with certificate checks, redirects refused, nothing cached on disk, and the password and token never printed or logged. The routes and the login come from Service Studio 11.55.95's client code and are tested against a local mock (`tests/server-check.ps1`) and live on a Personal Environment (Service Studio 11.55.97, password login; an external identity provider is not tested).
- **The skill is scanned with NVIDIA SkillSpector before each release.** `tests/skill-scan.ps1` runs `skillspector scan skill --no-llm --format json` offline (the skill declares no packages, so the OSV.dev lookup has nothing to send, and the proxy variables point at a closed local port) with the reviewed findings in `tests/skill-scan-baseline.yaml`, and fails above score 20. It skips with a message when SkillSpector is not installed (`OML_SKILLSPECTOR` or PATH). `release.ps1` runs it; `tests/regress.ps1` does not. SkillSpector 2.12.0 scored the skill 93/100 at first; four lines with the same meaning were reworded (two "no warning" lines read as anti-refusal, a "do not ask the user" line and a "no confirmation" line read as excessive agency), which brought it to 63, and the 13 remaining findings are reviewed false positives or intended behaviour: score 0 after the baseline, verdict CAUTION because two large reference files are only partly inspected. The README shows the result.
- **Skill evals in the skill-creator format.** `tests/skill-evals/trigger-evals.json` has 15 queries (8 that should load the oml skill, 7 near misses that should not) and `evals.json` 4 small task evals (refuse a rename, refuse an entity delete and ask before publish, the read-apply-validate loop, ODC to the OutSystems MCP). `tests/skill-evals/run-skill-evals.ps1` runs both with `claude -p` and `claude-haiku-5-5` by default, one run each, and writes the results to `tmp/skill-evals/`. It does on Windows what skill-creator's `run_eval.py` does (that script reads the stream with `select()`, which fails on Windows pipes). It sets no API key and is not part of any suite.
- **`--max-width N` and `--max-height N` for oml browser screenshots.** `page`, `look`, `try`, `sweep --out` and the screenshots of `run` shrink the PNG to fit, keeping its aspect ratio and never enlarging it. An agent pays for a picture by its pixels (about width x height / 750 tokens), not by its format, so a smaller picture is what saves tokens. - Two engines for `qa`: DevTools (`cdp`: real input events, the network, JavaScript errors) and Windows UI Automation (`uia`: a browser window left of all monitors, read through the accessibility tree). `--engine auto` uses `uia` when a `RemoteDebuggingAllowed = 0` policy blocks DevTools, as on many company PCs. `uia` has no network checks, JavaScript errors, key presses or `css:` targets. No new dependency: the DevTools client is a WebSocket, UI Automation is COM interop.
- `fill` checks every field again once the screen settles and types once more where a late data load reset it; the step notes it.
- `oml doctor`: the `browser` check says which engine `oml qa` uses and why.
- `oml qa record <url> [--out <qa.jsonc>]` writes a QA file from what you do in a visible window: clicks by widget Name, typed text and dropdown choices as `fill` and `select`, `expect screen` and `expect feedback` after clicks, passwords as `$env:QA_PASSWORD`. Fields the screen set itself go to `notes`. A recorded file replays with `oml qa run`.
- `oml qa start` and `oml qa stop` keep one browser open in a background process. `qa run` and `qa page` use it (`"session": true`): no browser start and the login stays. A second run of an 8-step file took 8.6 s instead of 15 s; `qa page` 1.2 s instead of 7 to 8 s. `--no-session` opts out.
- Layout checks: `qa page` lists `layout` findings (`overflow`, `small` click targets under 24 x 24 px, `overlap`) and the real `viewport`. New `expect` keys `inView` (no scrolling needed) and `layout`.
- Ready waits for the OutSystems screen transition to end (one `active-screen` in `#transitionContainer`). Before, a step could act while the old and new screens were both on the page.
- UI Automation engine: the ready wait listens for structure, name and value change events instead of reading the page every 80 ms, and reuses one read of the page until it changes. A click step costs about the app's own transition time; checks after it take 20 to 50 ms instead of about 700.
- `oml evolve`: a learning loop from local evidence. `report [--since] [--file]... [--check|--review <json>]... [--md]` shows where agents lose turns: failures that repeat, retries and the option change that made them pass, spec keys that fail, warnings looked up often, searches with no good hit, trap records agents still hit, check rules found often. `propose` writes proposals, each line citing usage-log lines or memory ids: trap records as `oml memory add` commands and a draft company skill per command family (`.oml/skills/evolved-<family>.md`); `--maintainer` writes unified diffs for `skill/reference/*.md`. `show`, `accept <id>`, `reject <id> [--why]` (remembered: never proposed again), `history` and `undo <id>`. `report` compares failure rate and median turns before and after each accepted proposal and marks it `helped`, `no effect` or `worse` with the undo command. Never `rules.md`; a lesson that could weaken a production rule, holds a secret or reads like an instruction is a flag for a person, not a proposal.
- `oml memory recall` learns from the usage log: records whose recalls were followed by passing commands rank higher, failing ones lower; of two live records that contradict, only the newer is shown (`overrides`); `fact`, `trap`, `answer` and `log` records nobody recalled for 180 days are left out (`stale`, `--include-stale`). `memory list` shows `use` and `stale`.

## 1.4.0

### Images: ICO, PNG to SVG, SVG optimization

- `oml image <input> --to ico [--sizes 16,32,48]` writes a real multi-size icon from any raster image or SVG (each size drawn from the vector). Frames up to 48 pixels are 32-bit BMP with a transparency mask, larger ones PNG. A non-square image is centred on a transparent square. Default sizes `16,32,48` (favicon); `--sizes 16,24,32,48,64,128,256` for an app icon. A size list with a word, an empty item, a repeat or a size outside 1-256 is refused, and so are `--sizes` without `--to ico` and `--max-width`/`--max-height` with it. Windows' own icon loader, `System.Drawing.Icon` and Chrome read the files.
- ICO input now always works (before: "this build may not support ICO"): oml reads the file itself and takes the largest frame, PNG or BMP (32-bit, 24-bit and palette frames with their transparency mask). A cut-off or foreign file gets a clear error, and so do a PNG frame over 100 million pixels (checked before decoding) and a palette larger than its colour depth. ICO input needs an explicit `--to`. A very wide image is scaled down before it is padded to a square, so a 20000 x 100 strip stays small in memory.
- `oml image <logo.png> --to svg` traces a raster image to vector paths (our own code, no Potrace or other GPL code): a palette from the flat colours (auto, at most 16; `--colors N`), one `<path>` per colour, layers that overlap so no background shows between colours, sub-pixel outlines from the anti-aliasing, sharp corners, cubic Béziers within `--tolerance` pixels (default 0.3), holes kept, speckles under `--min-area` removed, `--alpha-threshold`. For a photo or gradient the report adds a note that suggests `--mode embed`, which puts the PNG inside an SVG as it is; semi-transparent areas (shadows) also get a note. `--transparent-bg` leaves out a background colour that fills the border. Alpha at exactly `--alpha-threshold` counts as opaque. Lower layers reach only 2 pixels under higher ones, so thin letters next to bolder ones stay clean, and narrow line ends keep both corners. Tracing options on an SVG input are refused (noted in a batch). Before, raster to SVG was refused. On four test drawings (two-colour logo, flat icon, text, shapes with holes) at most 0.08% of the pixels differ from the source PNG; a 1024 x 1024 logo traces in under a second.
- SVG to SVG is now an SVGO-style optimizer (our own code): editor data, definitions without an id, empty groups, safe initial values and needless groups go; colours and path data take their shortest form; transforms are applied to paths and neighbouring paths merged when nothing can see the difference. The default is safe for `<img>`, inline SVG under page CSS and sprites: it keeps every id with its definitions, style attributes, explicit inherited values such as `fill="#000"` and element names, and leaves transforms with `transform-origin`/`transform-box` alone. `--remove-ids` drops ids and definitions nothing in the file uses; `--aggressive` (for `<img>` and CSS backgrounds only) adds that, style attributes to presentation attributes, inherited initial values and shapes to paths. Title, desc, text and the viewBox stay; a `<style>` element keeps the structure, scripts and animation keep every element. The default precision follows the viewBox size. Every result is drawn with Svg.Skia against the original: if the pixels change, a higher precision is tried, and otherwise the original bytes are written with `details.kept` and the reason. A plain DOCTYPE (old editors) is now accepted; one with its own declarations is still refused. `--strip-title` also removes `<desc>`. On 47 real SVGs: 36.5% smaller by default (36.7% with `--aggressive`), and Chrome draws every result like its original.
- `oml image batch <folder> --to ico` and `--to svg` (traces raster images, optimizes SVGs). An empty or missing batch folder is now an error (exit 2).
- `oml setup`: new right-click entries **oml: Convert to ICO** (images) and **oml: Trace to SVG** (raster images; a photo shows the note).
- New regression check `tests/image-check.ps1`.

### Preview: scripts and interactions

Before, code that used `controller` failed with "controller is not defined". The OnInitialize, OnReady and OnRender nodes run in flow order (OnInitialize parent first; OnReady and OnRender blocks first); a node that throws or rejects stops the rest of its action. A flow If whose condition the preview can evaluate (literals and inputs with `=`, `<>`, `not`; not when a value does not match its declared type, texts differ only in case, or an Assign changes the input) follows one branch; another If or a Switch runs every branch and a note names it. The dashboard reads `scriptErrors`.

An Image widget with a remote URL no longer loads it.

- Block events (Reactive and Mobile). A block declares `events` (name, `mandatory` default true, `inputs`), fires one with the flow node `triggerEvent` (only in the block's own client actions), and a BlockInstance handles them with `"events": { "<Event>": "<action>" }` or `{ "action", "args" }`. A handler input with no arg gets the event input of the same name; any other unmatched handler input is refused. An instance without a handler for a mandatory event is refused, naming the event. Blocks also take `onParametersChanged`. `describe` shows events, `trigger` lines and instance handlers. ### Production rules

- Rule 4 (public signatures) is precise: no type change, no new mandatory input, no input made mandatory; no input change at all on a public Reactive or Mobile block or screen; an optional input (or making an input optional) is safe only on public server and service actions and Traditional Web blocks and screens; a new output is safe only on public server and service actions. Rule 3 (no renames or deletes) is unchanged.
- Rules: an existing block's events are contract elements (rule 3: no rename, no delete). A new event on an existing public block, a new mandatory event on any existing block, and making an existing event mandatory are refused (rule 4). The send action `Send<Email>` that oml creates is not public.
- Fixed: listing an existing entity, structure or static entity in a spec without `public` made it private, because a missing `public` meant false (1.3.0 and earlier). Consumers in other modules then broke after publish. Now a missing `public` keeps the element's own setting (also for actions and content files), and apply refuses making an existing public element private, through spec keys and `edits.set` (rule 4).
- Rule 4 is enforced for inputs and outputs on every path (creation lists, `addVariables`, `addParts`, `set`): on an existing public element apply refuses a new mandatory input, an input made mandatory, a type change, any input change on a public client action or a public Reactive or Mobile block or screen, a new output except on server and service actions, and a type change of an event input on a public block. Before, a listed public action could get a new mandatory input. Making an input optional stays allowed on server and service actions and Traditional Web blocks and screens.
- Rule 7: only a server action that becomes public needs the user's OK. Apply allows it, new or existing (private to public, through spec keys and `edits.set`), and adds a `PublicServerAction` entry to `newWarnings` with the hint "Ask the user. If they say no, remove `public` from the spec and apply again from the same source." More than 12 such server actions are named in one message. Every other element (entities, structures, static entities, blocks, screens, client actions, roles, and so on) may become public with no warning. Service actions get no warning, because other modules call them by design; exposed REST methods have no public setting. Public to private on an existing element stays refused (rule 4), now for every kind with a public setting: images, scripts, resources, themes and process activities too (before, an existing public image, script, resource or theme could be made private with `edits.set`). Images, scripts and resources listed again take `"public": true`. A block made public in the same spec may get a new optional event: rule 4 holds for blocks that were public before the apply. Rules 4 and 7 read word for word the same in `rules.md`, the Copilot instructions and the website; the README sums them up. Only `entity-with-crud` keeps public server actions; the other recipes keep them private, and recipes without a caller for them report `UnusedUserAction`. The `unused-action` fix in `oml check` says to ask the user before making an action public.
- A name the model would rename (a "name taken" problem) now names the element that holds it: kind, owner and a path that `describe`, `tree` and `edits` accept (checked by the write rules of element paths), for example `name taken by input parameter Status of block LatticeLoader (path MainFlow/LatticeLoader/Status)`. Before, the message said "by a generated CRUD action or another element". This covers creation lists, `addParts`, `rename` edits, `copy`, content files, static entities and their attributes, indexes, aggregate groups, REST integrations, references and aliases, emails, extensions, flow nodes, UI flows and exception handlers. A clash names a referenced element rather than a flow node that calls it, and a variable's problem names it after the label (`block LatticeLoader: local Status: name taken by ...`).
- A unique index on an existing entity is now a `UniqueIndexOnExistingEntity` entry in `newWarnings` (it was in `warnings`), so the agent explains it to the user.

### Speed

- Add `--timings`: a command that loads a module (`apply`, `inspect`, `describe`, `validate`, `install`, `new`, `census`, `tree`, `find`, `preview`, `openapi`, `architecture`, `check`) adds a `timings` object with milliseconds per phase (`startup`, `serviceStudioInit`, `load`, `rules snapshot`, `save scratch`, `build logic`, `save`, `reopen`, `json`, ...). `oml run --timings` adds it to every step. The commands that run without Service Studio (`spec`, `doc`, `lt`, `doctor`, ...) refuse it with exit 2. Without the option the output does not change. `skill/reference/commands.md` lists the phases.
- `apply` skips the scratch save and reload of the data model when the spec has only logic keys (actions, blocks, screens, edits, REST, timers, processes, variables, system events, emails, locales, translations, folders, `tidyFlows`). The data phase then changes nothing, so the reload gave the same model. It saved 1.3 to 1.7 s per apply on the measured modules (the reload, and the slow first read of the reloaded model in flow layout). A spec with any data key reloads as before.
- In `oml run`, `apply` takes the module that an earlier step left open (same file, not changed on disk) instead of loading it again, when the file has the same write time, length and SHA-256 as when it was loaded. The module leaves the cache, so a later step that reads the source loads the file again. The scratch module of the data phase is now closed at the end of the apply; before, it stayed open for the rest of an `oml run` or a dashboard session.
- `install` loads the staged file once. It writes the validated bytes to the target and checks the target's SHA-256 against them, instead of loading the same bytes a second time (0.4 to 0.8 s on the measured modules). A read-only target is refused before the backup. A write that fails and leaves the target unchanged (a file another program holds open) says `Nothing installed` and keeps the backup; a write that changed the target restores the backup and says so.
- Reflection lookups (element names, properties, methods, widget and node types) are cached per type. A from-scratch build of 150 entities with 300 server actions, 300 screens and 51 blocks was about 4 s faster in the first measurement (29.9 s to 25.6 s); later runs on a busier machine showed 32.2 s to 29.9 s.
- The launcher runs without dynamic PGO (`TieredPGO` false): every command is a short process, so it only added JIT work. Measured 7 to 18 percent faster per command.
- Measured on the biggest real module found (2.3 MB `.oml`) and a synthetic module (2.8 MB, 41,000 objects), lowest of 3 runs, same machine. Apply with logic only: 5.6 s to 4.4 s (real), 8.2 s to 5.8 s (synthetic). Apply with data and logic: 6.1 s to 5.3 s, 8.4 s to 7.5 s. Install: 2.9 s to 2.4 s, 3.6 s to 2.7 s. An `oml run` of inspect, describe, apply, validate and apply on the synthetic module: 13.9 s to 9.0 s. About 1.5 to 2 s of every command is Service Studio's own start-up (`serviceStudioInit`), which oml cannot shorten; `oml run` pays it once.

### Fixes
